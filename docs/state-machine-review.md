# State machine review

This review follows state through the Action's main/post processes, GitHub records, workflow jobs, and release workflow. It covers explicit discriminated unions and implicit state represented by booleans, optional fields, serialized strings, API responses, timers, and branch refs. Findings below were reproduced locally with mocked GitHub responses; likelihood is an estimate of how often the required conditions occur, not measured incident frequency.

## Confirmed defects and fixes

All five defects below have focused regression coverage. No dependency, public input/output, version, or release changes are needed.

| Rank | Severity | Likelihood | Defect and impact | Fix and reproduction |
| --- | --- | --- | --- | --- |
| 1 | P2 | Moderate when deploying PRs with non-default bases | `BEHIND` describes the PR's own base, but freshness checks applied it to a separate stable branch. `outdated_mode: default_branch` could reject a PR already current with that branch or unnecessarily enter branch-update handling. | [Freshness checks](../src/functions/outdated-check.ts) now use the shortcut only for the actual base commit. [Regression tests](../__tests__/functions/outdated-check.test.ts): different base/stable SHAs, `BEHIND`, and stable comparison `behind_by: 0` previously returned `outdated: true`; it now returns `false`. Same-base and genuinely outdated cases remain covered. This matches [the documented scenario](outdated_mode.md#scenario-4). |
| 2 | P2 | Low; requires a slow confirmation response | Confirmation could accept the actor's approval after the deadline, or request another reaction page after time expired. | [Confirmation polling](../src/functions/deployment-confirmation.ts) checks the deadline after every awaited page, before examining reactions. [Two regressions](../__tests__/functions/deployment-confirmation.test.ts) advance the fake clock past the deadline with an approval response, or exactly to the deadline with a full page. Both failed before the fix; neither permits late admission or another page afterward. |
| 3 | P2 | Low; requires a successful write with a lost response | GitHub could create the lock ref and then fail the response. Acquisition threw before saving the ref SHA, leaving a blocking lock that the failed deployment did not know it acquired. | [Lock acquisition](../src/functions/lock.ts) performs one readback after a non-conflict error and records success only if the ref points to its exact candidate commit. [Regressions](../__tests__/functions/lock.test.ts) publish the ref and then throw a network error or HTTP 500. Both previously threw; they now save the acquired SHA. Missing, unreadable, and different refs preserve the error. No second ref write is issued. |
| 4 | P2 | Low; requires failure of the initial status write | Deployment creation could succeed, but failure writing `in_progress` caused main to bypass post and release its non-sticky lock. The deployment record stayed pending, or in progress if the status write itself succeeded before its response was lost. | [Deployment orchestration](../src/functions/deployment-operation.ts) now attempts an `error` status on that same deployment before cleanup. [Regressions](../__tests__/main.test.ts) verify `in_progress` failure → `error` → unlock, no continuation, and preservation of the original failure if the compensating status also fails. Both failed before the fix. A second API failure still requires manual record reconciliation. |
| 5 | P3 | Certain after an ordinary early initialization failure; uncommon overall | Required-input, input-parsing, or GitHub-client initialization errors happened before `isPost` was saved. The runner's post invocation could dispatch main again, repeating the failed initialization instead of selecting post. | [Main dispatch](../src/main.ts) now saves `isPost` before initialization. A two-import reproduction changed from two validation calls and zero post calls to one of each. [Main regressions](../__tests__/main.test.ts) cover missing token, malformed result-mode/timeout inputs, and client failure; [dispatch tests](../__tests__/main-post-dispatch.test.ts) verify the persisted flag selects post. |

## State inventory

The Action does not run the physical deployment itself. A successful main invocation emits continuation outputs; consumer workflow steps perform the mutation, and post or result mode reports its outcome. GitHub records and runner state therefore form separate parts of the lifecycle.

## Important transitions

| Current state | Event | Next state and required effect |
| --- | --- | --- |
| Main initialization | Input/client error | Failed with `isPost` and `bypass` saved; the runner's next invocation selects post. |
| Unpublished lock candidate | Ref response lost, readback equals candidate SHA | Acquired; record SHA before continuing. A different/unreadable ref remains an error. |
| Awaiting confirmation | Approval page returns at/after deadline | Timed out; no approval and no further reaction page. |
| Confirmed/prechecked | CI selection or selected ref changed | Stop; no consumer continuation; conditionally clean the original non-sticky lock. |
| GitHub deployment created | Initial status write fails | Attempt `error`, preserve original failure, bypass post, then conditionally clean the lease. |
| Active consumer work | Final success/failure | Record final status, conditionally release non-sticky lock, update labels. |
| Deferred completion | Cancelled selected job | Report non-success and retain the original lock. |
| Automatic cleanup | Current ref differs from saved SHA | Preserve the replacement lock. |
| Release verified | Major alias update fails | Exact immutable release remains; workflow fails and rerun validates existing artifacts before retrying progress. |

## Remaining boundaries and hypotheses

These are distinguished from the reproduced defects above; no broader policy or architecture changes are included.

- **Confirmed operational boundary: no durable recovery worker.** Hard process termination, runner loss, or force cancellation can prevent post/finally execution. There is no lock TTL or restart sweeper. Persisted locks and deployment records may require manual reconciliation. Same-owner reuse is intentional; [workflow concurrency](locks.md#actions-concurrency) must serialize physical mutations where needed.
- **Confirmed operational boundary: GitHub writes are not exactly once.** A lost deployment-creation response can leave a record whose ID was never received. Repeated result invocations can duplicate reporting or status writes; [result mode requires one invocation per context](result-mode.md#reruns-and-recovery). The lock fix has exact immutable candidate evidence; deployment creation has no equivalent idempotency key in this implementation. This change adds no application-level deployment retry or reconciliation; existing Octokit transport retries can still duplicate successful writes after a lost response.
- **Confirmed operational boundary: cleanup/reporting can be partial.** Normal post warns if conditional deletion fails and may still report completed; result and merge cleanup recheck the original lock and fail if it remains. Label/report failure can follow successful deployment recording. A compensating error-status write can also fail; the warning and deployment ID support manual reconciliation. Broadly changing these established completion semantics needs a separate policy decision.
- **Confirmed timer boundary:** the confirmation deadline prevents accepting a late answer but does not abort an HTTP request already in flight. Completion can therefore return after the configured timeout if GitHub is slow. There are no detached polling tasks or callbacks that can later authorize deployment after this function has returned.
- **Hypothesis: admission policy can change while waiting.** Ordinary PR draft/review policy and promotion history can change without changing the selected commit. Current rereads cover CI policy, selected check identity, refs, and full stack snapshots, but do not freeze all external admission conditions. No additional requirement that these conditions remain valid through deployment creation was established, so this review does not classify those races as confirmed policy violations.
- **Hypothesis: external pagination is not an atomic snapshot.** Existing cursor/count/identity checks reject many mutations across pages, but GitHub can still change records between reads. No additional bypass was reproduced. Forced branch update also lacks an expected-head condition, but it stops this attempt instead of deploying the changed head.

## Validation scope

The regressions exercise the transition failures without touching a live repository's deployment records, locks, comments, workflow settings, tags, or releases. The complete repository checks, coverage contract, generated-bundle reproduction, and local bundled main/post acceptance are the validation targets for this change. Live IssueOps acceptance and release publication are outside this review's execution scope; local API fault injection is the evidence for the confirmed error paths.
